# 找店与今天吃什么：优先级收敛（2026-11-02）

用户选择优先优化“找店与吃什么决策”。本轮基于既有功能矩阵继续实现：让用户先找到候选，再用真实可比信息作决定。其余交易/社交/运营扩展保持原矩阵的取舍。

## 发现与实施

| 原问题 | 双端调整 | 边界 |
|---|---|---|
| 手机先看到地图/API占位，找店入口在后 | Web竖屏将搜索/筛选/选店清单前置；Android默认进入找店模式 | 无地图Key仍可浏览和决策；主动查看地图或设置后再使用地图 |
| 只随机抽一家，难比较也容易反复抽回 | 最多三家并列比较店名、分类、地址、参考人均、评价和直线距离；可主动点“从本组选一家”结束纠结 | 随机不是推荐排名，不声称实时营业或消费验证；最终只打开详情，导航仍需主动点击 |
| 相邻抽选只排除上一家，仍可能长期遗漏 | 会话内不放回抽选，整轮候选耗尽后才开始新轮 | 本轮末组可能不足3家；候选变化自动重开；已看过结果不会写入个人历史 |
| 想尝新时仍混入吃过的店 | 决策面板可勾选本次避开“吃过” | 只读本机足迹，不上传；清单本身不改动 |
| 附近只能排序，不能限定范围 | 成功定位后可选500米/1/3/5公里 | GCJ-02直线距离，非步行距离/时间；未定位前控件明确不可用 |
| 筛选后不知道还保留了哪些限制 | 主清单和选店面板显示当前范围、预算/评分/清单等约束及候选数 | 无结果不自动扩大预算或范围，提供明确调整入口 |
| 重置不清搜索、无结果难恢复 | 双端统一重置搜索及筛选；空列表提供清除入口 | 位置仍仅在本次会话内存，Key和私人清单不受影响 |
| 定位请求切换后旧超时可能中断新请求 | Android超时仅关闭同一次请求，并区分浏览/投稿定位意图 | 地图认证、定位权限和真实精度仍需真机验证 |

视觉契约继续为 `ark + maximal`：黑白青信息系统，桌面目录/地图分区、独立选店对比模式；竖屏优先找店任务。用真实候选数、剩余数和筛选状态驱动布局，不加入虚构推荐分或装饰仪表。动效遵循减少动画设置。Web使用既有“索引/操作区/详情档案”的公开模式，新增比较区只服务临时决策。

## 实现与文件

- `web/public/decision.js`：纯抽选轮次模型，去重ID、候选范围变化重置、不修改输入、更新后读取最新公开字段。
- `web/public/discovery.js`：范围筛选；未知价格与实际0元继续区分。
- `web/public/{app.js,index.html,style.css}`：选店对话框、三家对比、吃过排除、范围/约束提示、列表优先与回到原地点焦点。
- `android/app/src/main/java/com/guet/foodshare/DecisionDeck.kt`：原生会话抽选模型。
- `android/app/src/main/java/com/guet/foodshare/MainActivity.kt`：原生决策面板、附近范围、清单入口和定位状态修正。
- `web/test/decision.test.mjs`：不放回轮次、重开边界、范围变化、空/单个/重复ID、数据刷新、半径/未知价格检查。
- `web/test/ui-ci.mjs`：远程检查单候选、无候选、7个候选3+3+1、不重复、吃过排除、预算重置和手机首屏入口；另上传选店截图。

只改客户端与远程回归，无新增D1迁移、不改公开数据协议、不向生产写测试地点。公开地点为空时，正式页面如实显示没有候选，不使用测试门店充数。
